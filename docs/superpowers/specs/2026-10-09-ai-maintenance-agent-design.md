# HerLink DeepSeek AI Maintenance Agent Design

## Goal

Add a safe AI maintenance agent for HerLink that can receive bugs from automatic detection or manual admin assignment, use DeepSeek to diagnose and propose repairs, apply only narrowly allowed code changes on an isolated repair branch, verify the result with GitHub Actions, and stop after at most two repair attempts.

This feature is only for software maintenance. The existing user-facing AI companion/chat feature is out of scope and must not be extended as part of this work.

## Safety invariants

1. The agent must never write directly to `main` or any production branch.
2. The agent must never merge a pull request or trigger a production deployment.
3. The agent must never modify Supabase migrations, production schema, production rows, or delete production data.
4. The agent must never read, expose, rotate, or modify repository/deployment secrets.
5. The agent must not execute arbitrary shell commands generated by the model.
6. The agent must not delete repository files during the safe-trial phase.
7. Every model-proposed action must pass server-side schema validation and an explicit allowlist before execution.
8. A repair job gets at most two automated repair attempts. After the second failed verification it stops as `needs_human`.
9. Every attempt must preserve an audit record: source bug report, diagnosis summary, proposed files, actual changed files, verification result, failure summary, attempt count, branch, commit, and PR when created.
10. Existing HerLink production behavior must remain unchanged until a human explicitly reviews and merges an approved repair PR.

## Scope

### In scope

- Manual bug assignment from the HerLink admin area.
- Automatic intake from narrowly defined system/CI error sources.
- DeepSeek diagnosis of supplied error evidence and relevant repository context.
- Creation of a dedicated repair branch per job.
- Allowlisted text-file edits inside application/test code.
- Test/typecheck/build verification through GitHub Actions.
- One retry using the first verification failure as additional evidence.
- Draft PR creation after a successful verification.
- `needs_human` terminal state after two failed attempts or any blocked operation.
- Admin-visible job status and audit trail.

### Out of scope for the safe trial

- AI companion/chat behavior.
- Direct production logins or browser operation by DeepSeek.
- Database migrations or production data repair.
- Dependency upgrades or lockfile changes.
- Workflow-file changes generated by the agent.
- Secret/environment-variable changes.
- Automatic PR merge.
- Automatic production deployment.
- File deletion.
- Unlimited repair loops.

## Architecture

The system is split into six bounded components.

### 1. Intake

Accepts either an admin-submitted bug or an allowlisted automated error event. It normalizes the report into a repair job containing a title, description, error evidence, source, affected surface, and timestamp.

The automatic path must initially accept only sources that HerLink can authenticate and normalize reliably. Unknown payloads are rejected rather than passed directly to the model.

### 2. Context collector

Collects only the repository context needed for the bug: relevant source files, tests, package scripts, and recent verification output. It does not provide secrets, environment values, production database contents, or unrelated user conversations to DeepSeek.

### 3. DeepSeek diagnosis/planner

Calls DeepSeek server-side using `DEEPSEEK_API_KEY`. The model receives the normalized bug report plus bounded repository context and returns structured repair intent.

The model may request only declared maintenance tools. Tool arguments are treated as untrusted input. The executor parses and validates them before any action. Invalid JSON, unknown tool names, extra parameters, forbidden paths, or oversized changes cause the job to stop for human review rather than falling back to permissive behavior.

### 4. Policy/executor

The executor is the security boundary. DeepSeek cannot directly call GitHub, Supabase, Vercel, a shell, or deployment APIs.

Allowed operations in the safe trial are intentionally small: read allowlisted repository files, propose replacements/patches to allowlisted application or test files, create/update a job-specific repair branch, commit those edits, request verification, and create a draft PR after successful verification.

Blocked paths include at minimum:

- `supabase/migrations/**`
- `.github/workflows/**`
- `.env*`
- secret/config files containing credentials
- generated deployment configuration where modification could trigger production behavior
- production data scripts

The executor also rejects deletion operations and any write targeting `main`.

### 5. Verification/retry controller

Each repair attempt runs the repository's existing verification path through GitHub Actions. The controller records the exact check result.

If attempt 1 fails, the failure output is supplied as new evidence for attempt 2. Attempt 2 starts from the isolated repair branch and may revise the proposed code within the same safety policy. If verification fails again, the job becomes `needs_human` and no further automatic write is allowed.

If verification succeeds, the controller creates or updates a draft PR against `main`. It does not merge it.

### 6. Admin UI

The admin area exposes a dedicated AI maintenance view, separate from any user-facing AI helper. It supports manual bug assignment and displays:

- job source and description
- current status
- attempt number (`1/2` or `2/2`)
- diagnosis summary
- changed files
- verification result
- branch/commit/PR reference
- blocked-action reason when applicable
- final `ready_for_review` or `needs_human` state

## Job state model

A job uses explicit states so the UI and controller cannot infer safety-critical behavior from free text:

- `queued`
- `diagnosing`
- `editing`
- `verifying`
- `retrying`
- `ready_for_review`
- `needs_human`
- `blocked`

`ready_for_review`, `needs_human`, and `blocked` are terminal for automatic execution. A human may later start a new repair job, but the old job is never silently resumed.

## Data/storage strategy

The safe trial must not require a new Supabase migration. Job persistence should reuse an existing suitable administrative persistence mechanism if one already exists; otherwise use GitHub-native artifacts/issues/PR metadata for the trial rather than adding a production database table.

A later version may introduce a dedicated database table only after separate explicit approval and migration review.

## DeepSeek contract

DeepSeek is a reasoning/planning dependency, not the authority that performs actions. The server owns all credentials and execution.

The model contract must return structured fields for diagnosis, confidence, proposed operation, target paths, rationale, and whether more evidence is needed. Tool/function-call arguments must be schema validated. The model must never receive an unrestricted `run_command`, `write_database`, `deploy`, `merge`, `delete_file`, or secret-access tool.

For the first version, prefer deterministic non-thinking tool-selection where required by the chosen API contract; if thinking mode is used, the client must preserve the API-required reasoning/tool-call conversation state correctly.

## Repair branch and PR rules

Every repair job gets a unique branch derived from a safe prefix such as `ai-repair/<job-id>` and based on the current approved `main` head at job creation time.

The agent may commit only to that branch. A successful job produces a draft PR targeting `main`. No auto-merge is enabled. The PR body summarizes the original bug, AI diagnosis, attempts, changed files, and verification results.

If `main` advances materially before PR creation, the job must re-check its base or stop for human handling rather than force-update production history.

## Error handling

- DeepSeek unavailable/timeout: record the failure and stop or retry only within the two-attempt budget; never bypass the model/policy boundary.
- Invalid model output: reject it; do not guess missing parameters.
- Forbidden path/action: mark `blocked` and show the reason to the admin.
- GitHub write failure: do not retry destructive operations; preserve the error for human review.
- Verification failure: feed the relevant failure evidence into the second and final attempt.
- Verification infrastructure outage: distinguish infrastructure failure from a code-test failure where possible; do not claim the repair failed because CI itself was unavailable.
- Concurrent jobs: each uses its own branch and job identifier; jobs must not write to one another's branches.

## Testing strategy

Tests must cover the policy boundary before enabling automatic writes.

Required coverage includes:

1. direct `main` write is rejected;
2. Supabase migration edits are rejected;
3. workflow edits are rejected;
4. `.env`/secret paths are rejected;
5. delete-file requests are rejected;
6. unknown tools and malformed model arguments are rejected;
7. valid allowlisted source/test edits are accepted on an `ai-repair/*` branch;
8. attempt 1 failure permits exactly one retry;
9. attempt 2 failure becomes `needs_human`;
10. successful verification produces only a draft PR and never merges/deploys;
11. manual and automatic intake produce the same normalized job contract;
12. concurrent jobs cannot cross-write branches;
13. companion/chat code paths are not required for the maintenance agent and remain behaviorally unchanged.

## Rollout

The initial rollout is admin-only and safe-trial only. Automatic detection can be enabled only for the allowlisted error sources included in the implementation plan. Manual assignment remains available so the site owner can test the full pipeline deliberately.

The safe trial is considered successful when a representative harmless test bug can be submitted, diagnosed, repaired on an isolated branch, verified, and surfaced as a draft PR without any direct production, database, secret, deployment, or merge action.
