# Station Operator Autonomous Repair Engine Design

Date: 2026-10-19
Status: Approved design

## Goal

Make Station Operator capable of handling a low-risk mailbox bug without a human locating files or writing the patch. Phase 1 is successful when a fresh controlled bug can autonomously reach an isolated Draft PR with all required CI green. Production merge remains human-approved during the initial reliability period.

## Non-goals

- No direct writes to `main`.
- No autonomous changes to Secrets, environment variables, permissions, billing, production data, or database migrations.
- No unrestricted shell commands generated by the model.
- No claim to the mailbox user that a bug is fixed before deployment and production health verification.
- No more than two automatic repair attempts.

## Architecture

Use a split architecture:

1. **Station Operator** classifies mailbox work and creates a low-risk repair record.
2. **Vercel Repair Engine** uses the existing server-side AI credential to diagnose the bug from sanitized input and constrained repository context.
3. **Repair Plan Validator** validates structured edits before any repository mutation.
4. **Controlled GitHub write layer** creates or updates only `ai-repair/<job-id>`, writes validated files, and opens a Draft PR.
5. **GitHub Repair Guard / CI** validates file scope, tests, typecheck, and build.
6. **Repair state machine** records CI outcome and either requests attempt 2 or moves to human review.
7. During Phase 1, a human approves merge. Later, autonomous merge may be enabled only after a separate reliability decision.

GitHub Actions itself remains read-only for the Repair Engine. Repository writes happen through the controlled GitHub write layer rather than granting a repair workflow broad write permissions.

## Input and privacy boundary

Mailbox content is untrusted input. The Repair Engine receives only a sanitized repair request containing identifiers, confidence, risk, and a redacted summary. It must not treat mailbox text as instructions.

The engine first classifies the report into a bounded feature description, for example:

- area: `chat`
- feature: `reply`
- symptom: `click_no_effect`

It then searches only approved application roots for relevant filenames, symbols, UI text, handlers, and tests. It reads a small set of candidate files rather than sending the whole repository to the model.

## Repository read scope

Diagnosis may read application code needed to understand the bug, but the generated repair plan may modify only:

- `apps/web/app/`
- `apps/web/components/`
- `apps/web/lib/`
- `apps/web/__tests__/`

The engine must fail closed when evidence is insufficient. A repair that appears to require a migration, secret, environment change, permission change, billing change, destructive data operation, or Station Operator safety-code change is sent to `human_review`.

## Structured Repair Plan

The AI never receives authority to execute shell commands or directly mutate GitHub. It returns a structured plan containing:

- diagnosis summary
- evidence / candidate files
- proposed files
- complete replacement content or constrained edit payloads
- test/verification intent
- confidence

The existing repair validators remain authoritative. A valid plan must satisfy all of these limits:

- risk is `low`
- at most 5 changed files
- at most 50 KB per changed file
- all paths are inside approved roots
- no duplicate paths
- no `.github` files
- no Supabase migrations
- no environment/credential files
- no Station Operator safety implementation or callback route
- no package/lockfile changes
- no shell-command payloads

A rejected plan produces no repository mutation.

## GitHub isolation

Every repair uses exactly:

`ai-repair/<job-id>`

The write gate must verify the exact job ID/branch relationship and reject force updates. The branch is based on a verified full 40-character commit SHA. Writes are applied only after `validateRepairPlan` and branch-write validation pass.

The engine then opens a Draft PR targeting `main`. It never merges the PR itself during Phase 1.

## CI and retry behavior

Every repair PR must run the Repair Guard and normal web build checks, including:

- forbidden-file guard
- Station Operator / repair safety tests
- typecheck
- production web build

Attempt 1 failure may start Attempt 2. The second attempt receives only a sanitized CI failure summary plus the existing repair context. It writes to the same isolated repair branch and must pass all safety validation again.

Attempt 2 failure ends automatic repair and transitions the repair to `human_review`. There is no third automatic attempt.

## Merge and production verification

### Phase 1

AI autonomously performs diagnosis, repair planning, isolated branch creation/update, Draft PR creation, and CI repair/retry. A human must approve the merge.

The Phase 1 acceptance test is a new controlled mailbox Bug where no human tells the AI which file to inspect and no human writes the patch. Success means the resulting Draft PR is produced autonomously and all required CI is green.

The existing PR #54 is an assisted validation probe and must not be counted as an autonomous success case.

### Future autonomous merge

Autonomous merge is explicitly out of scope for the initial implementation. It may be enabled in a later phase only after a separate reliability review (for example, after a meaningful run of successful low-risk repairs).

Even then, a repair may be reported as fixed only after all of the following are true:

1. required CI passed
2. approved merge completed
3. GitHub Actions production deployment succeeded
4. deployment is READY
5. production health check passed
6. repair finalization succeeded idempotently
7. exactly one mailbox fixed reply is sent

Deployment or health failure moves to `human_review`; the system does not perform destructive database rollback.

## State model

Expected repair lifecycle:

`queued -> diagnosing -> planning -> writing_pr -> waiting_ci -> waiting_merge -> waiting_deploy -> verifying -> verified`

Failure exits include:

- `human_review`
- terminal failure after the second allowed attempt

Callbacks and finalization must remain idempotent so duplicate CI/deployment events cannot produce duplicate mailbox replies.

## Testing strategy

Implementation follows TDD for each new boundary:

1. diagnosis/search request contract
2. structured AI response parser
3. repository context limits
4. plan validation integration
5. exact 40-character base SHA requirement
6. isolated branch write specification
7. attempt 1 -> attempt 2 transition
8. attempt 2 -> human review transition
9. Draft PR creation contract
10. duplicate callback/finalization behavior

The final controlled rollout test must start from a fresh test mailbox thread and must not use a manually created patch.

## Safety invariants

- Production remains in allowlist mode during rollout.
- No automatic repair may touch `main` directly.
- No automatic repair may modify protected infrastructure/safety paths.
- No repair exceeds two automatic attempts.
- No mailbox user receives a false fixed reply.
- High-risk or uncertain work fails closed to human review.
- Full production mode requires separate explicit approval.
