# HerLink 匿名身分自助恢復設計

## 目標

讓失去瀏覽器匿名身分的使用者，可憑自己的永久恢復碼自行接回原匿名身分與既有聊天室，不再需要站長逐筆判斷 A/B 方；同時保留現有管理員人工恢復作為遺失恢復碼時的備援。

## 已確認產品規則

- 自助恢復入口沿用首頁「無法進入原本聊天室？」流程。
- 恢復碼改為永久有效，不再以 30 分鐘作為一般自助恢復期限。
- 恢復碼為一次性憑證：成功恢復後立即失效，並為恢復後的身分產生新的恢復碼。
- 恢復成功後採單一裝置接管：新裝置取得匿名身分控制權，舊裝置立即失效。
- 保留既有管理員人工恢復，供恢復碼遺失、已刪除或其他無法自助驗證的案件使用。
- 不允許只靠匿名名稱恢復身分。

## 架構

將「恢復申請」與「永久身分恢復憑證」分離。現有 `anonymous_session_recovery_requests` 與管理員 `admin-reactivate-session-recovery` 繼續服務人工救援，不把既有 30 分鐘申請資料直接當成永久憑證。

新增匿名身分層級的永久恢復憑證。資料庫只保存恢復碼的不可逆雜湊與必要的輪替/撤銷狀態，不保存可直接使用的明碼。自助恢復只能由伺服器端函式完成，前端不得直接更新 profile、session 或訊息擁有關係。

## 資料模型

新增 `anonymous_identity_recovery_tokens`（名稱可依現有 migration 命名慣例微調）：

- `id uuid` 主鍵
- `profile_id uuid`：原匿名身分
- `token_hash text`：恢復碼雜湊，唯一
- `created_at timestamptz`
- `used_at timestamptz null`
- `revoked_at timestamptz null`
- `replaced_by uuid null`：成功輪替後指向新 token

同一匿名身分只允許一組目前有效的永久恢復碼。舊碼一旦成功使用、主動撤銷或被輪替，不可再次使用。

## 自助恢復流程

1. 使用者在「無法進入原本聊天室？」選擇「使用恢復碼」。
2. 前端取得目前瀏覽器的新匿名身分 UUID，連同使用者輸入的恢復碼送至伺服器端自助恢復函式。
3. 伺服器正規化恢復碼、計算雜湊並查找有效 token。
4. 驗證 token 未使用、未撤銷，且目標匿名身分仍存在。
5. 回傳最少量確認資訊，例如匿名名稱與可恢復聊天室數量；不回傳對方完整私人訊息作為驗證資料。
6. 使用者確認後，以單一 transaction 執行接管：將目前裝置/session 的有效匿名身分憑證切換到原 profile，撤銷舊裝置的身分控制權，保留原 profile、聊天室、訊息、匿名聯絡人、未讀和彩蛋/成就資料的既有關聯。
7. 將本次 token 標記 `used_at`，建立新的永久恢復碼並回傳一次給新裝置保存/顯示。
8. 前端清除新建臨時匿名身分的本地識別資料，改使用恢復後身分並重新載入聊天室。

## 單一裝置接管

恢復成功後必須增加匿名身分的 session/credential generation（或沿用專案既有等價機制）。所有需要匿名身分授權的伺服器端操作均驗證 generation。恢復 transaction 提升 generation，使舊裝置持有的舊 generation 立即失效。

不得只替換 localStorage UUID；否則舊裝置仍可能繼續操作同一身分。

## 臨時新身分處理

自助恢復前目前瀏覽器可能已建立新的匿名 profile。成功接管後，不直接刪除可能已有資料的 profile。若它完全沒有聊天室、訊息、聯絡人或其他使用者資料，可由既有清理機制日後清除；若已有資料則保留，避免恢復動作造成資料遺失。第一版不自動合併兩個匿名身分的聊天紀錄。

## 安全

- 恢復碼視同密碼，不記錄明碼到資料庫、分析事件或一般 application log。
- 使用密碼學安全亂數產生恢復碼；維持目前使用者熟悉的 8 碼格式時，必須搭配嚴格 rate limit。若現有基礎設施無法可靠限速，實作時應提高碼長而非降低安全要求。
- 依 IP 與目前匿名身分雙重限速；連續錯誤達門檻後暫時鎖定嘗試。
- 查無此碼、已使用、已撤銷等情況對前端使用相同失敗文案，避免探測有效碼。
- 自助恢復函式使用 service-role 權限並自行做完整授權檢查，不開放資料表直接寫入。
- 建立恢復 audit，記錄時間、來源匿名 UUID、目標 profile、結果與 token id，但不記錄恢復碼明碼。

## 人工恢復相容性

現有 `anonymous_session_recovery_requests`、管理後台恢復 A/B 方與 `admin-reactivate-session-recovery` 保留。人工恢復成功後也應撤銷目標 profile 既有永久恢復碼並產生新碼，避免舊碼持有人再次接管。

舊的 30 分鐘恢復申請不自動轉換成永久恢復碼。像已刪除的舊申請仍走人工核對，不因本功能重新變成有效憑證。

## UI

「無法進入原本聊天室？」內提供兩條清楚路徑：

1. `我有恢復碼`：輸入永久恢復碼 → 確認匿名身分 → 自助恢復 → 顯示新恢復碼。
2. `恢復碼遺失`：沿用目前聯絡站長/建立人工恢復申請流程。

成功頁必須提醒使用者保存新的恢復碼，並明確說明舊恢復碼已失效、舊裝置已登出。

## 錯誤處理

- 無效/已使用/已撤銷碼：顯示統一錯誤，不洩漏碼是否曾存在。
- 目標 profile 不存在：交易不執行，轉人工處理。
- transaction 任一步失敗：全部 rollback，舊 token 仍保持原狀，不產生半恢復狀態。
- 新 token 建立失敗：整筆恢復 rollback，不能先讓舊碼失效。
- 網路中斷後重送：伺服器必須能辨識已成功完成的恢復，避免第二次轉移。

## 驗收條件

- 有有效永久恢復碼的使用者可在新瀏覽器自行恢復，不需管理員操作。
- 原匿名名稱、原聊天室與訊息紀錄保持不變。
- 成功後舊裝置無法再以舊匿名 credential 發訊息或修改資料。
- 成功使用的恢復碼無法再次使用，並產生一組新碼。
- 錯誤碼不能取得任何原聊天室內容。
- 多次錯誤嘗試會被限速。
- 恢復過程失敗不會留下半完成的 profile/session 關聯。
- 管理員原本的人工恢復流程仍可正常使用。
- 人工恢復後舊永久恢復碼同步失效。
- 現有聊天室、訊息與聯絡人資料不因導入此功能被批次改寫。

## 部署原則

先完成 migration、伺服器端函式與自動測試，再接 Web UI。正式啟用前以管理員測試身分完整驗證「產碼 → 新瀏覽器 → 自助恢復 → 舊裝置失效 → 新碼輪替」，確認不影響現有人工恢復後才開放一般使用者。
